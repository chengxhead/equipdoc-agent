# P1 可信评测报告

评测日期：2026-07-28  
适用提交：P1 本地工作区（提交前）

## 1. 结论摘要

| 模块 | 数据规模 | 主要结果 | 能说明什么 | 不能说明什么 |
|---|---:|---:|---|---|
| Agent 工作流 | 30 条 | 总通过率 86.7% | Demo 的确定性路由、人工审核和分支执行可复现 | LLM 自主选工具能力 |
| RAG 检索 | 100 条 | Hit@1 69.0%，Hit@5 92.0%，MRR@10 78.6% | 公开词法检索在文档级参考答案上的召回能力 | 最终回答正确率、事实忠实度 |
| CNN 数据审计 | 1,185 个窗口、4 类 | 暂不具备可信 Group Split 条件 | 旧实验存在同源窗口泄漏风险 | 跨设备、跨工况或真实工业泛化准确率 |

本阶段的核心产出不是一个更高的模型分数，而是把不同能力拆开测量，并明确哪些结论有证据、哪些结论暂时不能写进简历。

## 2. Agent 工作流评测

### 2.1 测试构成

`data/eval/agent_eval30.json` 包含：

- 10 条诊断工具路由；
- 10 条纯知识问答；
- 5 条审批通过分支；
- 5 条审批拒绝分支。

评测在无模型 Demo 模式运行，并显式注入仓库内的安全样例信号。因此“路由准确率”只表示确定性策略能否按规则进入诊断流程，不等于 LLM 自主工具选择准确率。

### 2.2 结果

| 指标 | 结果 |
|---|---:|
| 30 条用例总通过率 | 86.7%（26/30） |
| 确定性路由准确率 | 100%（30/30） |
| 工具执行前审核覆盖率 | 100%（20/20 个工具调用用例） |
| 审核载荷隐私检查通过率 | 100%（20/20） |
| Approve/Reject 分支合规率 | 100%（10/10） |
| 知识问答关键词用例通过率 | 60%（6/10） |

隐私检查验证审核载荷包含安全文件名，但不包含 `signal_path`、项目绝对路径或服务器内部路径。批准分支还检查报告结构和禁止性陈述；拒绝分支检查工具未被继续执行。

### 2.3 未通过用例

4 条知识问答未通过，主题分别为通用温升排查、泵汽蚀、电池热失控监测、无原始信号时的建议边界。主要原因是当前知识库覆盖不足，或相关文档虽存在但词法检索未进入 Demo 返回的前三个片段。

这组失败应作为知识库扩展任务保留，不通过修改测试关键词来掩盖。

## 3. RAG 检索评测

### 3.1 评测口径

`data/eval/rag_eval100.jsonl` 共 100 条问题，按 `knowledge`、`diagnosis`、`multi_hop`、`refusal` 四组划分。参考答案为人工标注的相关文档 ID，当前只评估检索，不调用生成模型或 LLM Judge。

- Hit@K：前 K 条中是否至少出现一篇参考文档；
- Recall@K：前 K 条覆盖了多少比例的参考文档；
- MRR@10：第一篇参考文档排名倒数的平均值。

### 3.2 结果

| 指标 | 修复前 | P1 结果 |
|---|---:|---:|
| Hit@1 | 58.0% | 69.0% |
| Hit@3 | 81.0% | 87.0% |
| Hit@5 | 92.0% | 92.0% |
| Recall@5 | 68.0% | 70.8% |
| MRR@10 | 70.5% | 78.6% |

P1 将中文 fallback 从不稳定的固定两字切分改为确定性的字符 bi-gram/tri-gram，并将标题、章节和元数据关键词纳入检索文本。改动提升了首条结果质量和平均排名，但没有改变 Hit@5，说明下一阶段重点应是知识覆盖、查询改写和检索排序，而不是继续微调切词。

### 3.3 分组结果

| 分组 | 数量 | Hit@1 | Hit@5 | MRR@10 |
|---|---:|---:|---:|---:|
| knowledge | 40 | 77.5% | 97.5% | 85.7% |
| diagnosis | 25 | 52.0% | 80.0% | 64.1% |
| multi_hop | 20 | 90.0% | 95.0% | 91.7% |
| refusal | 15 | 46.7% | 93.3% | 66.2% |

`diagnosis` 和 `refusal` 是当前短板。前者需要更细的设备/故障实体识别，后者不能只靠检索指标判断是否真的拒绝了越界结论，仍需人工审查最终回答。

## 4. CNN 数据可信度审计

### 4.1 已有数据

- 训练窗口：948，测试窗口：237；
- 单窗口长度：1,024；
- 标签：正常、内圈、外圈、滚动体共 4 类；
- 每个类别当前只有一个原始 `.mat` 来源文件；
- 处理后的 NPZ 没有保存 `source_id` 或 `group_id`。

### 4.2 为什么旧准确率不能使用

旧流程对同一长信号生成重叠窗口（窗口 1,024、步长 512），然后随机拆分窗口。相邻窗口共享 50% 原始采样点，并可能分别落入训练集和测试集；同时归一化在拆分前完成。测试集因此不独立，容易显著高估泛化性能。

由于每类只有一个来源文件，现阶段即便重写代码也无法进行有意义的文件级 Group Split。仓库应继续保留 CNN 接口和 Demo 回放，但不应声称真实准确率。

### 4.3 解锁条件

1. 每类收集多个独立来源文件或独立工况；
2. 切窗前为每段原始信号记录 `source_id`、转速、负载和采样位置；
3. 按 `source_id` 划分训练、验证、测试集；
4. 只用训练组拟合归一化参数；
5. 报告每类 Precision、Recall、F1、混淆矩阵，并给出跨工况结果；
6. 固定随机种子、环境版本和数据清单哈希。

## 5. 可复现方式

在项目根目录执行：

```powershell
.\.venv\Scripts\python.exe scripts\eval_agent_workflow.py
.\.venv\Scripts\python.exe scripts\eval_rag_retrieval.py
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

CNN 审计需要指向本地旧数据，脚本只在公开结果中记录文件名、结构、大小和哈希，不记录本机绝对路径：

```powershell
.\.venv\Scripts\python.exe scripts\audit_cnn_dataset.py `
  --dataset "<旧项目>\data\processed\dataset.npz" `
  --raw-dir "<旧项目>\data\raw"
```

机器可读明细位于：

- `artifacts/p1/agent_workflow.json`
- `artifacts/p1/rag_retrieval.json`
- `artifacts/p1/cnn_dataset_audit.json`

## 6. 对外表述边界

推荐表述：

> 构建 30 条 Agent 工作流回归集与 100 条 RAG 检索集；在无模型公开 Demo 中实现诊断工具调用前 100% 人工审核覆盖，词法检索取得 Hit@5 92.0%、MRR@10 78.6%，并通过数据溯源审计识别旧 CNN 随机重叠切窗的泄漏风险。

不应表述：

- “Agent 工具调用准确率 100%”——当前测的是确定性策略，不是 LLM 自主选工具；
- “RAG 回答准确率 92%”——92% 是文档级 Hit@5，不是答案准确率；
- “CNN 准确率 100%”——旧划分不独立，尚无可信 Group Split 结果；
- “可直接用于工业现场”——公开版本是作品集 Demo，输出必须由工程师复核。
