# EquipDoc-Agent 面试讲解话术与追问应答

## 1. 30 秒项目介绍

> EquipDoc-Agent 是一个面向机电设备运维的可审核 Agent。它把自然语言问答、振动信号检查、轴承 CNN 分类、RAG 证据检索和人工审核组织成 LangGraph 工作流。Qwen 只输出受 Schema 和工具白名单约束的计划，高影响诊断必须 Approve/Reject；最终技术回答需要可回查引用，信息不足或高风险请求会主动澄清或拒绝。

## 2. 90 秒项目介绍

> 这个项目要解决的不是普通设备问答，而是三个工程问题。第一，大模型不能直接读取振动时序，需要调用专用信号工具；第二，工具调用不能完全交给模型自由发挥，尤其诊断可能影响维修判断；第三，运维回答必须说明依据和边界，不能编造设备信息或精确寿命。
>
> 我的实现分成三层：LangGraph 负责状态和人工中断；确定性策略负责意图约束、工具白名单、参数 Schema、步数上限和高风险边界；Qwen 负责受限规划和证据组织。知识检索和信号统计是只读工具，CNN 诊断必须审核。回答中的技术陈述绑定 `doc_id#chunk_id`，草稿校验失败时不会直接展示。
>
> 项目经历了 P2.1 到 P2.2 的优化。已归档 P2.2 Fix 3 快照在64-turn正式集上为64/64，p95从16.758秒降到9.926秒，38个证据回答全部进入结构化路径。随后为 Full 页面增加规划热修复，指定演示问题已不再降级，但当前代码的正式复测是63/64；因此我会区分评测快照与当前运行版本，不把旧结果移植到新代码。

## 3. 推荐的项目故事线

面试中按以下顺序讲，不要按代码目录顺序讲：

1. **业务风险**：运维回答会影响现场判断，不能只追求能回答；
2. **系统拆分**：LLM、确定性策略和专用工具职责分离；
3. **关键约束**：工具白名单、路径注入、人工审核、Answer Guard；
4. **真实失败**：P2.1 全部证据回答 fallback、调用次数多；
5. **通用整改**：证据槽位、聚焦检索、现场复核动作证据、减少重试；
6. **量化结果**：三轮 Demo、64-turn、延迟下降和路径分布；
7. **诚实边界**：规划 fallback、人工复核、知识权威性、CNN Group Split。

## 4. 架构讲解

可以把系统概括成：

```text
用户输入/信号
  → 确定性安全预检
  → Qwen 结构化计划
  → Schema、工具白名单和步数校验
  → 只读工具直接执行 / CNN 诊断等待人工审核
  → 工具观察和短期记忆
  → 证据槽位选择
  → 带引用的结构化回答
  → Answer Guard 或安全降级
```

重点文件：

| 文件 | 面试中怎么解释 |
|---|---|
| `agent/agentic_graph.py` | LangGraph 节点、条件边、审核中断和观察后决策 |
| `agent/planning.py` | 严格 JSON 计划、Schema、意图校验和确定性 fallback |
| `agent/knowledge_answer.py` | 证据槽位、引用验证、结构化答案和 Answer Guard |
| `agent/agentic_tools.py` | 三工具统一执行边界和路径注入 |
| `tools/bearing.py` | `.npy` 沙箱校验、信号统计和 CNN 接口 |
| `rag/retriever.py` | 词法/Dense 检索、聚焦过滤和显式降级 |
| `scripts/eval_agentic_full.py` | 真实模型评测合同、路径诊断和延迟统计 |

## 5. 高频追问

### 为什么用 LangGraph，而不是普通链式调用？

> 因为这个流程包含人工中断、恢复执行、多轮状态和条件路由。普通顺序 Chain 很难表达“工具调用前暂停，用户审核后从原状态继续”。LangGraph 的 checkpoint 和 interrupt/resume 更适合这种可恢复工作流。

### 为什么不用原生 Function Calling？

> 当前 Qwen 服务是 OpenAI-compatible 文本接口，项目采用严格 JSON Prompt 加本地 Schema 校验。重点不是模拟原生 Function Calling，而是证明模型输出必须经过工具白名单、参数清洗和步数限制后才能执行。后续替换成原生工具调用时，确定性执行层仍可复用。

### Qwen 和规则分别负责什么？

> Qwen 负责理解任务、生成受限计划和尝试组织证据；规则负责不能出错的边界，例如剩余寿命、远程控制、工具权限、路径、审核和引用有效性。最终稳定性来自两者组合，不依赖模型单独保证安全。

### 64/64 是否代表模型准确率 100%？

> 不是。它表示模型重试、确定性 fallback、工具和 Answer Guard 组合后的最终输出满足冻结合同。52 个规划 turn 中只有 26 个模型计划被首轮或重试接受，另外 26 个用了确定性 fallback，所以不能说规划准确率 100%。

### 为什么 fallback 这么高？

> 当前 7B 模型对严格 JSON、意图约束和工具参数同时满足的稳定性有限。项目选择失败时显式进入确定性路由，而不是放宽工具权限。下一步会按格式、意图、参数和工具选择拆分失败原因，针对性优化 Prompt 或使用更强模型。

### 怎么降低幻觉？

> 不把“降低幻觉”当成一个无法验证的口号，而是拆成可检查约束：引用必须属于本轮检索集合；技术陈述需要句级引用；数字和术语不能超出证据；设备编号、历史趋势和精确寿命禁止编造；校验失败的草稿不展示。

### P2.1 为什么所有知识回答都会降级？

> 当时系统让 Qwen 选择证据，但校验器实际上要求它完整复现确定性 Top 4，模型只要选了不同但合理的证据也会失败；一次问答还可能触发多轮规划、选证据和综合重试。P2.2 把问题拆成证据槽位，由程序确保机理、特征和现场复核完整覆盖，再让模型在受控证据上工作。

### 结构化证据答案是不是另一种模板？

> 是受约束的结构化渲染，但不是固定内容模板。章节结构由问题意图决定，具体句子来自本轮检索证据。这样牺牲了一部分自由表达，换取可回查、可测试和更稳定的面试演示。项目不会把它包装成模型自然生成能力已经完全解决。

### CNN 准确率是多少？

> 当前不报告工业准确率。旧实验的随机窗口划分可能让同一原始文件的相邻窗口进入训练和测试集，存在泄漏风险。需要按原始文件、设备或工况做 Group Split 后，才能报告可信的宏平均 F1 和混淆矩阵。

### 人工复核为什么没做？

> 当前先完成工程闭环和自动合同，人工复核暂时延期。因此不能报告人工正确率、人工 groundedness 或引用有用率。工作簿和评分维度已经准备好，后续需要人工逐 turn 审核。

### 如果用于生产，还缺什么？

> 至少还缺权威且带版本的设备手册、真实工况数据、CNN Group Split、人工 groundedness 复核、鉴权审计、持久化存储、监控告警、模型版本管理，以及与现场维修流程的权限集成。

### 延迟是怎么优化的？

> 主要不是换硬件，而是减少无效 LLM 调用。没有引用或明显无法通过 Answer Guard 的综合草稿不再重复生成，而是直接使用已经通过槽位检查的结构化证据答案。正式集 p95 因此从 16.758 秒降到 9.926 秒。

## 7. 推荐说法与禁止说法

| 不建议说 | 推荐说 |
|---|---|
| Agent 准确率 100% | 已归档 Fix 3 快照的冻结64-turn自动合同为64/64；当前Live代码为63/64 |
| Qwen 工具调用准确率 100% | 26/52 模型计划被接受，其余由确定性 fallback 接管 |
| 回答完全没有幻觉 | 最终回答经过引用、术语、数字和安全边界校验 |
| CNN 准确率 100% | CNN 工具链可运行，但工业准确率尚未完成可信 Group Split |
| 支持预测轴承剩余寿命 | 明确拒绝仅根据单段信号输出精确寿命 |
| 已经达到工业生产标准 | 已形成可复现工程原型，仍需权威知识、真实数据和生产治理 |

## 8. 20 秒收尾

> 这个项目让我认识到，工业 Agent 的关键不是让模型尽量自由，而是设计好模型失败时系统仍然安全、可解释、可复现的路径。我保留了失败演进、fallback 分布和未完成的人工与 CNN 评估，确保项目指标可以被追问和复核。
