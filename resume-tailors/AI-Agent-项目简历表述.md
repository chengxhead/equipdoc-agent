## 4. 改写策略

- Agent 开发版本优先写“架构动作 + 评测口径 + 真实结果 + 失败边界”，突出工程闭环，不使用模糊的“负责大模型开发”。
- AI 产品经理版本优先写“场景问题 + 产品机制 + 指标体系 + 基于失败样例的迭代”，弱化底层代码细节。
- 两个版本都保留14/20严格通过率，不把引用原文匹配100%写成回答正确率100%。
- CNN不写准确率；如果面试官追问，应主动说明旧数据存在同源窗口泄漏风险。

## 6. 可直接复制的简历版本

### A. Agent 开发 / LLM 应用工程版本

**EquipDoc Agent｜机电运维智能体（个人项目）**  
`LangGraph / Qwen2.5-7B / RAG / Gradio / FastAPI / GitHub Actions`

- 面向机电设备知识问答与轴承信号诊断场景，基于 LangGraph 构建工具路由、状态管理和 Approve/Reject 人工审核工作流，将自然语言交互、专用诊断工具与维修决策边界解耦，并提供可复现的 Demo/Full 双模式。
- 设计设备/故障聚焦检索、Qwen证据句ID选择、逐句 `doc_id#chunk_id` 引用和确定性降级链路；针对初始真实模型回答无引用及 BPFO/BPFI/BSF 混淆，增加逐句引用覆盖与引用原文匹配守卫，避免为错误生成机械补引。
- 在 RTX 4090 上部署 Qwen2.5-7B OpenAI-compatible 服务并完成20条 Full 模式评测：20/20请求成功，严格通过14/20，平均必需关键词召回91.25%，引用原文匹配率100%，一次预热后的串行端到端 p95 为0.433秒；定位多子问题证据选择不完整为主要误差来源。
- 建立30条 Agent 工作流、100条 RAG 检索和20条高风险边界回归集，当前分别达到100%工作流通过率、Hit@5 91.0% / MRR@10 76.8%和100%固定安全用例通过率，并接入 GitHub Actions；对旧CNN数据发现同源窗口泄漏风险，因此主动撤回不可复现的准确率声明。

### B. AI 产品经理版本

**EquipDoc Agent｜机电运维AI产品原型（个人项目）**

- 基于机械专业背景定义“设备知识问答 + 轴承诊断辅助”场景，将产品拆分为公开可复现 Demo 与真实模型 Full 两种模式，并设计上传校验、工具调用审批、证据引用、风险提示和人工复核等关键流程，避免模型直接替代维修决策。
- 建立“工作流正确性—检索召回—高风险边界—真实模型回答”四层评测体系，覆盖30条 Agent、100条 RAG、20条安全和20条 Full 用例；真实模型评测严格通过14/20、平均关键词召回91.25%，并区分自动门槛、引用可追溯性和人工正确率三种口径。
- 基于失败样例推动产品机制迭代：从自由生成改为“聚焦检索—模型选择证据—系统确定性渲染—失败显式降级”，将引用有效率和原文匹配率提升至100%；同时保留证据选择不完整、知识来源权威性不足和真实用户指标缺失等限制。

## 9. 面试复用提示

高概率追问：

1. 为什么不让Qwen直接生成最终答案？
2. 引用原文匹配100%为什么不等于回答正确率100%？
3. 14/20失败在哪里，为什么没有继续把测试调到100%？
4. BM25和Chroma分别在什么情况下使用？
5. 人工审核节点解决什么风险，哪些操作必须拦截？
6. 为什么撤回CNN准确率，窗口级随机划分有什么问题？
7. 如果继续迭代，如何解决多子问题证据选择遗漏？

回答时按“问题发现—证据—工程决策—指标变化—仍存边界”展开。最有价值的项目故事不是最终数字，而是从无引用且含技术错误的真实模型回答出发，建立可审计链路，并保留70%严格通过率而没有继续针对固定测试集过拟合。
